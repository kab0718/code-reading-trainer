# MVP実装計画

## 1. この文書の目的

Code Reading TrainerのMVPを、動作確認可能な小さな単位に分けて実装するための作業手順を定める。

最初からすべての機能を並行して作るのではなく、まず自由トレーニングの一連の体験を完成させ、その後におまかせトレーニングを追加する。

## 2. MVPの前提

- 対象はGitHub上のpublic repository
- 対応言語はPython
- Chrome Manifest V3のサイドパネル拡張として提供する
- ユーザーはPythonコードを読み、説明を1回だけ回答する
- 回答後に100点満点の総合点、観点別得点、良かった点、不足点、模範解答を表示する
- 回答前には模範解答を表示しない
- 回答の書き直しと再評価は初期版に含めない
- 複数ファイルを横断する解析やコード実行は行わない

## 3. 推奨する実装順序

```text
仕様確定
  ↓
自由トレーニングのUI完成
  ↓
評価APIとの接続
  ↓
採点結果・模範解答の表示
  ↓
おまかせ候補の抽出
  ↓
エラー処理・計測・リリース確認
```

自由トレーニングを先に完成させることで、候補抽出が未完成でも「コードを選ぶ、回答する、採点を見る」というプロダクトの中心体験を検証できる。

## 4. フェーズ0: 実装前の仕様確定

評価軸の配点、再配分、評価APIの入出力・入力上限・エラー・タイムアウトは、[評価仕様・API契約 v1](evaluation-api-contract.md) で確定済みとする。クライアントとAPIは `contracts/evaluation/v1/` のJSON Schemaを共通利用する。

### 作業

- 評価APIの配置先と実装方式を決める
- APIの利用者認証と利用回数制限を決める
- コード、回答、採点結果を保存するか決める
- AIへコードと回答を送信することの表示方法を決める
- Pythonファイルであることの判定方法を決める

### 推奨する初期方針

- 履歴は保存せず、現在のサイドパネル内だけで保持する
- Python判定はGitHub上のファイルパスが `.py` で終わることを基本とする
- 自由トレーニングでは選択範囲をそのまま評価対象にする
- AIの認証情報は拡張機能に埋め込まず、バックエンドの評価APIで管理する
- APIレスポンスは自由文ではなく、固定されたJSON形式にする

### 完了条件

- 未決事項が選択肢ではなく、実装時に参照できる決定として記録されている
- APIのリクエストとレスポンス形式が確定している
- 採点結果画面に必要なデータがすべてAPIレスポンスに含まれている

## 5. フェーズ1: 自由トレーニングの入力体験

### 作業

1. GitHubのコード画面かどうかを判定する
2. 開いているファイルがPythonか判定する
3. 選択されたコード、ページURL、ファイル情報をContent Scriptから取得する
4. 選択コードをサイドパネルに表示する
5. ユーザーが説明を入力できるようにする
6. 未選択、Python以外、空回答、長すぎる入力を検証する
7. 回答送信中は二重送信できないようにする

### 画面状態

- GitHub以外を開いている
- Pythonファイル以外を開いている
- コードが選択されていない
- 回答入力中
- 採点中
- 採点完了
- エラー発生

### 完了条件

- GitHub上で選択したPythonコードがサイドパネルに正しく表示される
- コード未選択時と空回答時に、次に行う操作が分かるメッセージが表示される
- 採点ボタンを押すと、コードと回答を評価処理へ渡せる
- HTMLとして解釈されることなく、コードと回答が安全に表示される

## 6. フェーズ2: 評価APIと採点ロジック

### 作業

1. 評価APIのエンドポイントを作成する
2. リクエストの形式とサイズを検証する
3. Pythonコードとユーザー回答をAIモデルへ渡すプロンプトを作成する
4. 対象コードに適用する評価軸をAIに判定させる
5. 観点別得点と総合点の整合性を検証する
6. AI出力を固定JSONへ変換し、不正な出力を拒否または再生成する
7. タイムアウト、回数制限、モデルエラーを処理する
8. URLや回答内容など、不要な情報をログへ残さないようにする
9. CloudflareアカウントとWorkers AIの無料枠を確認する
10. AI binding、Rate Limiting binding、許可する拡張機能ID、本番Origin制限を設定する
11. dry-run bundleを確認してWorkerをデプロイし、公開URLを拡張機能へ設定する
12. 本番URLで正常系、CORS、入力エラー、回数制限を疎通確認する
13. Neuron使用量とAPIエラーを監視し、ロールバック手順を確認する

Cloudflare固有の設定値、コマンド、デプロイ後の確認項目は[評価APIの構成と運用](evaluation-api-operations.md)を作業手順の正本とする。MVPではWorkers AIの無料割当を上限とし、有料プランや有料モデルへ自動移行しない。

### 評価APIのデータ契約

実装時は [評価仕様・API契約 v1](evaluation-api-contract.md) と `contracts/evaluation/v1/` を正本とする。以下は主要フィールドの概要である。

リクエスト:

```json
{
  "language": "python",
  "sourceUrl": "https://github.com/owner/repository/blob/main/example.py",
  "code": "def example(...):\n    ...",
  "explanation": "この関数は..."
}
```

レスポンス:

```json
{
  "requestId": "4fd0d833-6bad-4d6e-b2e2-7fd9ba73710b",
  "contractVersion": "1.0",
  "totalScore": 78,
  "criteria": [
    {
      "id": "purpose",
      "label": "目的・責務",
      "applicable": true,
      "baseWeight": 25,
      "score": 20,
      "maxScore": 25,
      "feedback": "処理の目的を説明できています。",
      "exclusionReason": null
    }
  ],
  "strengths": ["入力を検証している点を説明できています。"],
  "gaps": ["例外が発生する条件の説明がありません。"],
  "modelAnswer": "この関数は...",
  "evaluatedAt": "2026-08-15T12:00:00Z"
}
```

`criteria` は概要を示すため1件だけ記載している。実際のレスポンスは6軸を固定順で返す。

### API側で保証すること

- `totalScore` は0以上100以下の整数
- `score` は0以上 `maxScore` 以下
- 採点対象となる `maxScore` の合計は100
- `criteria` には6軸を固定順で含め、対象外軸は `applicable: false` として明示する
- `modelAnswer` はコードから判断できない事実を断定しない
- 模範解答は採点処理が完了するまでクライアントへ返さない

### 完了条件

- 複数の難易度のPythonコードに対して、形式の崩れていない採点結果が返る
- 同じコードと同程度の回答に対する点数が極端に変動しない
- 観点別の満点合計と総合点の計算に矛盾がない
- APIキーなどの認証情報が拡張機能の配布ファイルに含まれていない
- 対象のCloudflareアカウント、Worker名、公開URL、デプロイversionが作業記録に残っている
- 許可した拡張機能からのみ評価でき、本番でOriginなしのリクエストを許可していない
- Workers AIのNeuron使用量、4xx、5xx、タイムアウト、429を確認できる
- 直前の正常なversionへロールバックする手順を実施できる

## 7. フェーズ3: 採点結果画面

### 作業

1. 100点満点の総合点を表示する
2. 観点別の得点と満点を表示する
3. 良かった点と不足点を分けて表示する
4. ユーザーの回答と模範解答を比較できるように表示する
5. 採点後は同じ回答を再送信できないようにする
6. 新しいトレーニングを開始する操作を用意する
7. APIエラー時には回答を失わず、再送信できるようにする

### 完了条件

- 回答前に模範解答が表示されない
- 採点後に総合点、観点別得点、良かった点、不足点、模範解答がすべて表示される
- 1回限りの回答というルールが画面操作上も守られる
- 長いコードや長い模範解答でもサイドパネルのレイアウトが崩れない

## 8. フェーズ4: おまかせトレーニング

Pythonファイル本文の取得、関数・メソッドの構文範囲、対応構文、実装とテストの境界は、[Python関数・メソッド候補の抽出方式](python-candidate-extraction.md)を正本とする。

### 作業

1. 現在のPythonファイル本文を取得する
2. `def`、`async def`、クラス内メソッドの範囲を抽出する
3. デコレータを対象コードに含める
4. 短すぎる関数、単純なアクセサ、自動生成らしいコードを除外する
5. 残った候補をウォームアップ、おすすめ、チャレンジに分類する
6. 難易度、推定時間、推薦理由を表示する
7. 選ばれた候補を自由トレーニングと同じ回答・採点フローへ渡す

### 実装方針を決める際の比較対象

- ブラウザで利用できるPythonパーサーを拡張機能へ同梱する
- 評価API側でPython ASTを使って抽出する
- 初期版のみ、限定的なルールで候補を抽出する

正規表現だけで完全なPython構文を扱うことは避ける。複数行シグネチャ、デコレータ、ネストした関数、非同期関数を考慮して方式を選ぶ。

比較の結果、拡張機能へ `@lezer/python` を同梱してBackground Worker内で構文解析し、GitHub Contents REST APIから取得した本文を構文ノードの範囲で切り出す方式を採用する。採用理由と不採用方式の詳細は抽出方式の文書を参照する。

### 完了条件

- 一般的なPythonファイルから最大3件の候補を提示できる
- 候補として表示したコード範囲が途中で切れていない
- 候補が見つからない場合、自由トレーニングへ案内できる
- 候補選択後は自由トレーニングと同じ採点結果まで到達できる

## 9. フェーズ5: 品質確認とリリース準備

### 機能確認

- GitHub以外のページ
- GitHubのPythonファイル
- Python以外のファイル
- コード未選択
- 短いコードと長いコード
- 日本語の回答と英語の回答
- 正しい回答、不完全な回答、誤った回答
- APIタイムアウト、回数制限、サーバーエラー
- GitHub内でのページ遷移後の動作

### セキュリティとプライバシー

- APIキーや秘密情報が拡張機能に含まれていないことを確認する
- public repository以外を対象外にする
- AIへ送信するデータを送信前にユーザーへ示す
- ログへコードや回答を保存する場合は、目的と保存期間を明示する
- `innerHTML` を使わず、外部入力をテキストとして表示する
- APIに入力サイズ制限と利用回数制限を設ける

### 計測

最低限、次のイベントを区別して計測できるようにする。

- サイドパネルを開いた
- 自由選択またはおまかせ候補を選んだ
- 回答を提出した
- 採点結果と模範解答を表示した
- トレーニングを完了した
- エラーが発生した

コード本文や回答本文は、分析イベントへ含めない。

### 完了条件

- MVP必須機能を実際のGitHubページ上で一通り操作できる
- 正常系と主要な異常系の確認項目が記録されている
- Chrome拡張を新規に読み込んだ環境で再現できる
- 収集する情報と外部AIへの送信についてユーザーが確認できる

## 10. テスト方針

### 単体テスト

- GitHub URLとPythonファイルの判定
- 入力文字数と必須入力の検証
- 評価APIレスポンスの形式検証
- 観点別配点と総合点の計算
- Pythonの関数・メソッド候補抽出

### 結合テスト

- Content ScriptからSide Panelへのコード受け渡し
- Side PanelからBackground Workerを経由した評価API呼び出し
- APIレスポンスから採点結果画面への反映
- エラー発生時の回答保持と再送信

### 手動確認

- GitHubの画面構造が異なる複数のrepositoryで確認する
- サイドパネルの狭い幅で表示を確認する
- GitHub内のクライアントサイド遷移後にも動作することを確認する

- 回答の書き直しと再評価
- 学習履歴と過去回答の比較
- 評価の納得感に対するユーザーフィードバック

- 対応言語の追加
- VS Code拡張とのデータモデル共通化
