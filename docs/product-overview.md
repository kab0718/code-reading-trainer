# プロダクト概要

## 1. 背景

OSSのコードを読めるようになりたいと思っても、コードを眺めるだけでは理解できたつもりになりやすく、何を読めばよいかも判断しづらい。

一方、AIに最初からコードを解説させると、理解する前に答えを受け取れてしまい、コードリーディングそのものの練習になりにくい。実際のOSS調査では、どこに注目し、次に何を確認すべきか分からないまま読み進められなくなることもある。

本プロダクトでは、理解を説明して採点を受けるトレーニングと、実際のOSS読解で着眼点や段階的なヒントを得る読解サポートを提供する。AIが読解を代行するのではなく、ユーザーが自分でコードを読み解く過程を支援する。

## 2. プロダクトコンセプト

> OSSのコードを、自分の力で読み解けるようにする読解コーチ。

AIは用途に応じて2つの役割を持つ。トレーニングでは、ユーザーが回答したあとに点数、観点別のフィードバック、模範解答を提示する採点者として振る舞う。読解サポートでは、最初から完成した解説を渡さず、着眼点、確認質問、段階的なヒントを提示するコーチとして振る舞う。

## 3. 対象ユーザー

- OSSを読めるようになりたいソフトウェアエンジニア
- 業務で既存コードを追う力を伸ばしたい初級〜中級エンジニア
- 新しい言語やフレームワークを、実際のコードから学びたい人

初期版では、GitHub上のpublic repositoryにあるPythonコードを読むユーザーを対象とする。

## 4. コアとなる体験

```text
対象コードを決める
  ↓
目的を選ぶ
  ├─ トレーニング
  │    コードを読む
  │      ↓
  │    自分の言葉で説明する
  │      ↓
  │    点数・フィードバック・模範解答と比較する
  │
  └─ 読解サポート
       分からない点や調査目的を書く
         ↓
       着眼点・確認質問・ヒントを受ける
         ↓
       必要な場合だけ詳しい説明を確認する
```

トレーニングで重要なのは、模範解答を見る前にユーザー自身が説明することである。初期版では回答は1回限りとし、提出後に採点結果、フィードバック、模範解答をまとめて表示する。回答の書き直しと再評価は、将来の機能として検討する。

読解サポートで重要なのは、AIが調査や思考を代行しないことである。最初の応答は注目すべき処理や識別子、確認すべき前提、理解を進めるための質問を中心とし、詳しい説明はユーザーが明示的に求めた場合だけ提示する。

## 5. 対象コードの選び方

主導線は、システムが候補を提示し、ユーザーが最終的に選ぶ方式とする。

### おまかせトレーニング

現在開いているPythonファイルから、学習に向いた関数またはメソッドを最大3件提示する。

| 候補           | 狙い                                             |
| -------------- | ------------------------------------------------ |
| ウォームアップ | 短く、責務が比較的明確なコード                   |
| おすすめ       | 分岐や依存が適度にあり、説明する価値があるコード |
| チャレンジ     | 複数の処理や副作用を含む、やや難しいコード       |

各候補には、難易度、推定時間、推薦理由を表示する。ユーザーは候補をスキップしたり、別の候補を選んだりできる。

### 自由トレーニング

ユーザーがGitHub上で選択したコードを対象にする。調査中に気になったコードや、仕事で理解したいコードをそのまま教材にできる入口として提供する。

### 読解サポート

ユーザーがGitHub上で選択したコードと、分からない点または調査目的を対象にする。最初の応答では、以下を選択コードから判断できる範囲で提示する。

- 注目すべき処理や識別子
- 確認すべき前提、入出力、分岐、副作用
- 理解を進めるための確認質問
- 次に確認する関数や型の候補と、その理由

ユーザーは必要な場合だけ詳しい説明を追加で取得できる。MVPでは現在の選択コードだけをAIへ渡し、別ファイルの内容やリポジトリ全体について確定的な説明は行わない。

### 初期の選出基準

- 短すぎず、長すぎない
- 単純なgetter、setter、自動生成コードではない
- 適度な分岐や関数呼び出しを含む
- コメントや名前を見るだけでは処理内容が完全には分からない
- 現在のファイル内の情報を中心に説明できる

MVPでは高度なリポジトリ解析を行わず、現在開いているファイルを対象にする。

## 6. 説明の評価軸

配点、対象外軸の再配分、APIの入出力とエラー形式の実装上の正本は、[評価仕様・API契約 v1](evaluation-api-contract.md) とする。

初期版では、以下の観点をそれぞれ点数で評価し、総合点を100点満点で表示する。

| 評価軸     | 確認する内容                                              |
| ---------- | --------------------------------------------------------- |
| 目的・責務 | コードを逐語訳せず、何のための処理か説明できているか      |
| 入出力     | 何を受け取り、何を返すか理解しているか                    |
| 主要処理   | 重要な処理の流れを押さえているか                          |
| 分岐・例外 | 条件分岐、失敗条件、例外処理を理解しているか              |
| 副作用     | 状態変更、DB、API、キャッシュなどへの影響を認識しているか |
| 前提・依存 | 呼び出し先や入力について必要な前提を捉えているか          |

すべての観点を機械的に要求するのではなく、対象コードに存在する観点だけを採点対象とする。対象外の観点は採点から除外し、対象となった観点の配点を合計100点になるように調整する。

### フィードバックの原則

- 最初から模範解答を表示しない
- 点数だけで終わらせない
- 総合点と観点別の得点を表示する
- 正しく説明できている点を明示する
- 抜けている観点を具体的に示す
- 採点後に模範解答を表示し、ユーザー自身の説明と比較できるようにする

## 7. MVP

### 必須機能

1. GitHubのソースコード画面で拡張機能を起動できる
2. 選択したコードを自由トレーニングの対象にできる
3. トレーニングと読解サポートを選択できる
4. サイドパネルに自分の説明を入力できる
5. AIが100点満点の総合点、観点別の得点、良かった点、不足点を返す
6. 採点後に模範となる説明を確認できる
7. 読解サポートで分からない点または調査目的を入力できる
8. 最初に着眼点、確認質問、段階的なヒントを確認できる
9. ユーザーが希望した場合だけ詳しい説明を確認できる
10. 現在のファイルから、トレーニング対象の候補を提示できる

### MVPでは扱わないもの

- private repository
- 複数ファイルを横断する高度なリポジトリ解析
- コードの実行やデバッグ
- 対応言語の完全な構文解析
- チーム向け管理機能
- ランキングやソーシャル機能
- 長期的な習熟度分析
- 回答の書き直しと再評価
- 定義、参照、呼び出し元の自動追跡
- 読解経路や調査履歴の保存
- AIによる調査の自動完遂

回答の書き直しと再評価は、初期版の利用状況とフィードバックを踏まえて将来追加を検討する。

## 8. Chrome拡張を選ぶ理由

- GitHubを閲覧する普段の流れから、そのまま練習や読解サポートを始められる
- cloneやローカル環境構築が不要
- GitHubのコード表示を自前で実装する必要がない
- 関数・メソッド単体、ファイル単体の短時間の練習や読解と相性がよい

一方、呼び出し元、型定義、参照箇所、テストなどをリポジトリ全体から追う体験には限界がある。その段階ではVS Code拡張が適している。

## 9. 将来のVS Code拡張

Chrome拡張は選択コードを対象にした短時間の読解練習と支援、VS Code拡張はリポジトリを横断する本格的な読解と調査の支援として位置づける。

VS Code版では以下を検討する。

- 定義・参照・呼び出し元を追う課題
- 関連する型やテストコードを読む課題
- ユーザーが確認したファイルやシンボルの記録
- 調査経路に対するフィードバック
- 機能全体や設計意図の説明
- 実行・テスト・デバッグを含む演習

課題、回答、評価のデータモデルや評価APIは、将来Chrome拡張とVS Code拡張の双方から利用できる形を目指す。

## 10. 初期アーキテクチャ

```text
GitHubページ
  ├─ Content Script: ページ情報・選択コードの取得
  └─ Side Panel: モード選択・入力・結果表示
          ↓
     Background Worker
          ↓
  評価API / 読解サポートAPI
          ↓
       AIモデル
```

初期の拡張機能はUIとGitHub連携に集中させる。AIの認証情報を配布物へ埋め込まないため、公開を想定する段階では評価と読解サポートのAPIをバックエンドに置く。両者は認証、利用制限、ログ方針を共通化しつつ、入出力契約とクライアント状態を分離する。

## 11. 検証したい仮説

1. ユーザーは、AIの解説を読むより先に自分で説明を書くことを受け入れるか
2. 観点別の点数とフィードバックに納得感があるか
3. システム推薦された関数・メソッドから、迷わず練習を始められるか
4. 1回5〜10分程度のトレーニングを継続したいと思うか
5. 実際のOSS読解中に、着眼点や段階的なヒントが役立つか
6. ユーザーは詳しい説明を見る前に、自分でコードを読み進められるか
7. GitHub上の読解だけで不足を感じ、VS Codeでより深く読みたいと思うか

## 12. MVPの成功指標案

- 候補表示から回答提出までの到達率
- 回答提出から採点結果・模範解答表示までの完了率
- 1セッションあたりの完了トレーニング数
- 初回利用後7日以内の再利用率
- 自由選択とおまかせ選択の利用比率
- トレーニングと読解サポートの利用比率
- 読解サポート開始からヒント表示までの完了率
- ヒント表示後に詳しい説明を開いた比率
- 評価が納得できたかについての簡単な自己申告
