# 読解サポートAPI契約 v1

## 目的と分離方針

読解サポートAPIは、対象コードを自力で読むためのガイドと、明示操作後の詳しい説明を返す。採点、模範解答、トレーニングの1回限り状態は扱わず、評価APIとはエンドポイント、リクエスト、成功レスポンス、クライアント状態を分離する。CORS、公開GitHub URL確認、Rate Limiting、Workers AI bindingは共通利用する。

実装上の正本は `contracts/reading-support/v1/` のJSON Schemaである。

## エンドポイントと段階

`POST /v1/reading-support` を使用する。`stage` は次の2値とする。

| 値                     | 役割                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| `guide`                | 着眼点、確認事項、確認質問、段階的なヒント、次に確認する候補を返す。完成した解説は返さない |
| `detailed_explanation` | ユーザーの明示操作後に、候補コードだけを根拠にした詳しい説明を返す                         |

どちらの段階も同じコードを送る。ガイドは模範解答に必要な評価観点から自動生成し、ユーザーによる質問入力を要求しない。詳しい説明の取得時もサーバー側セッションや本文保存には依存しない。

## 入力・処理上限

- 対象言語: `python` 固定
- ソースURL: public GitHubの `.py` blob URL、最大2,048文字
- 対象コード: 1〜30,000文字
- HTTP body: 64 KiB以下
- API全体: 60秒、モデル呼び出し: 55秒、拡張機能通信: 70秒
- Rate Limiting: 評価APIと同じbindingを使い、Originと接続元IPの組み合わせに対して設定値どおり制限する。現在の `wrangler.jsonc` は60秒あたり10回

## 成功レスポンス

両段階で固定キーを返す。`guide` では4種類のガイド配列を1〜5件、詳しい説明を `null` とする。`detailed_explanation` ではガイド配列と候補を空にし、`detailedExplanation` を1〜5,000文字で返す。候補は対象コードに現れる関数・型・識別子から判断できる場合だけ、理由付きで返す。

モデル出力は固定Schemaで要求し、アプリケーション側でも未知キー、件数、文字数、段階別のnull・空配列規則を検証する。Pythonキーワードを除くコード識別子との境界付き照合に加え、生成結果を別の構造化モデル呼び出しで根拠検証し、範囲外の断定があれば表示せず再生成する。ガイドが1回の再生成後も不正・根拠不十分な場合や、モデル呼び出しが失敗・タイムアウトした場合は、対象コード内の識別子だけを使った定型ガイドへフォールバックする。無料利用枠の超過はフォールバックせず、従来どおり `RATE_LIMITED` を返す。詳しい説明もフォールバックせず、検証に通らなければ `READING_SUPPORT_MODEL_ERROR` とする。

## 根拠とプライバシー

- 対象コード以外のファイル、呼び出し元、実行結果、リポジトリ設計を取得したように断定しない
- 確認できない内容は「候補コードからは確認できない」と示す
- `sourceUrl` は公開状態確認にだけ使い、AIへ送らない
- コード本文をログ、計測イベント、履歴へ保存しない
- 利用開始、ガイド表示、詳しい説明表示、完了は、イベント名、時刻、モード、段階だけで計測する

## エラーと再試行

エラー形式は専用Schemaに従う。入力・認証・サイズ違反は再試行不可、回数制限、内部障害、モデル障害、タイムアウトは再試行可能とする。クライアントはエラー時も対象コードを保持し、`RATE_LIMITED` の `retryAfterSeconds` が過ぎるまで再送信を無効にする。
